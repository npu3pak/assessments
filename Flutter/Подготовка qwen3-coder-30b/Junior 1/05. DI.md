# Лекция: Внедрение зависимостей (Dependency Injection) в Flutter

## Введение

Внедрение зависимостей (Dependency Injection, DI) — это паттерн проектирования, который позволяет управлять зависимостями между компонентами приложения. Он обеспечивает гибкость, тестируемость и поддержку кода. Проще говоря, DI — это способ передачи зависимостей извне в класс, вместо того чтобы создавать их внутри.

В мире Flutter DI особенно важен, потому что приложение может быть разделено на множество модулей и сервисов, которые зависят друг от друга. Правильное использование DI помогает избежать жёстких связей между компонентами, упрощает тестирование и делает код более читаемым.

---

## 1. Описание принципов

### Что такое зависимость?

**Зависимость** — это объект или сервис, от которого зависит другой объект. Например:

```dart
class UserRepository {
  Future<User> fetchUser(int id) async {
    // ...
  }
}

class UserService {
  final UserRepository _userRepository;

  UserService(this._userRepository);

  Future<User> getUser(int id) => _userRepository.fetchUser(id);
}
```

Здесь `UserService` зависит от `UserRepository`, потому что он использует его в своём конструкторе.

### Принципы DI

1. **Инверсия управления (Inversion of Control)** — вместо того чтобы класс сам создавал зависимости, он получает их извне.
2. **Слабая связность** — компоненты не зависят напрямую друг от друга.
3. **Тестируемость** — можно легко подменить зависимости для unit-тестирования.

---

## 2. Способы внедрения зависимостей

### Вариант 1: Конструктор (Constructor Injection)

Наиболее распространённый способ — передача зависимостей через конструктор:

```dart
class ApiService {
  Future<String> fetchData() async {
    return 'data';
  }
}

class DataProvider {
  final ApiService apiService;

  DataProvider(this.apiService);
}

// Использование:
final api = ApiService();
final provider = DataProvider(api);
```

### Вариант 2: Метод внедрения (Method Injection)

Зависимость передаётся как параметр метода:

```dart
class DataProcessor {
  void process(ApiService service) {
    // используем сервис
  }
}
```

### Вариант 3: Свойство внедрения (Property Injection)

Используется, когда зависимость устанавливается через свойство:

```dart
class DataProcessor {
  ApiService? apiService;

  void process() {
    if (apiService != null) {
      // ...
    }
  }
}
```

## 3. Локатор сервисов и связанные с ним проблемы

### Что такое локатор сервисов?

**Локатор сервисов** — это паттерн, который предоставляет способ получения зависимостей по их типу или ключу. Пример: `getIt`, `kiwi`, `get_it`.

### Пример использования `get_it`:

```dart
import 'package:get_it/get_it.dart';

final getIt = GetIt.instance;

// Регистрация сервиса
getIt.registerSingleton<ApiService>(ApiService());

// Получение сервиса
final api = getIt.get<ApiService>();
```

### Проблемы локаторов:

1. **Скрытые зависимости** — при использовании `getIt.get<T>()` становится трудно понять, откуда взялась зависимость.
2. **Нарушение принципа инверсии управления** — класс получает зависимости не через конструктор, а через "волшебный" метод.
3. **Усложнённое тестирование** — сложнее подменить зависимости при тестировании.

### Проблемы:

- Нарушение **принципа открытости/закрытости (OCP)** — изменения в локаторе могут повлиять на множество компонентов.
- Возможность **создания глобальных точек отказа** — если один сервис не инициализирован, весь поток может сломаться.

## 4. Возможности и ограничения библиотеки Kiwi

### Что такое Kiwi?

**Kiwi** — это DI-библиотека для Dart/Flutter, которая предоставляет более строгую систему управления зависимостями по сравнению с `get_it`.

### Основные возможности:

- **Типобезопасность**
- **Поддержка жизненного цикла объектов (Singleton, Transient)**
- **Гибкая регистрация и разрешение зависимостей**

### Пример использования Kiwi:

```dart
import 'package:kiwi/kiwi.dart';

// Регистрация сервиса
Container().registerSingleton<ApiService>(() => ApiService());

// Получение сервиса
final api = Container().resolve<ApiService>();
```

### Ограничения Kiwi:

- Нет поддержки автоматического внедрения (только ручное)
- Не так прост в использовании, как `get_it`
- Меньше активности и документации по сравнению с другими библиотеками

## 5. Циклические зависимости. Способы решения проблемы

### Что такое циклическая зависимость?

Это ситуация, когда два или более класса зависят друг от друга напрямую:

```dart
class ClassA {
  final ClassB b;

  ClassA(this.b);
}

class ClassB {
  final ClassA a; // ошибка: ClassA ещё не завершён

  ClassB(this.a);
}
```

### Способы решения:

#### 1. **Использование интерфейсов**

Создайте интерфейсы и реализации, чтобы разорвать цикл:

```dart
abstract class IClassA {
  void doSomething();
}

class ClassA implements IClassA {
  final IClassB b;

  ClassA(this.b);

  @override
  void doSomething() {
    b.doSomethingElse();
  }
}

class ClassB implements IClassB {
  final IClassA a;

  ClassB(this.a);

  @override
  void doSomethingElse() {
    a.doSomething();
  }
}
```

#### 2. **Использование отложенного внедрения (Lazy Injection)**

Возможно с помощью `get_it` или `kiwi`, если они поддерживают ленивую загрузку:

```dart
// Пример с get_it
getIt.registerLazySingleton<ApiService>(() => ApiService());
```

#### 3. **Рефакторинг архитектуры**

Избегайте циклических зависимостей путём пересмотра архитектуры: вынесите общую логику в отдельный класс, который будет служить посредником.
