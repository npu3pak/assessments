# Лекция: GitLab для Flutter-разработчика уровня Junior

## Введение

GitLab — это мощная платформа управления версиями кода, которая предоставляет инструменты для совместной работы над проектами, автоматизации CI/CD и управления репозиториями. Для мобильного Flutter-разработчика GitLab играет ключевую роль в организации рабочего процесса, особенно при командной разработке.

---

## 1. Как сделать Merge Request

### Что такое Merge Request?

**Merge Request (MR)** — это запрос на слияние изменений из одной ветки в другую. В контексте GitLab он используется для предложений изменений в основную ветку проекта (например, `main` или `develop`). MR позволяет обсудить код, провести ревью и убедиться, что изменения корректны перед тем, как они попадут в продакшн.

### Шаги по созданию Merge Request

1. **Создайте новую ветку**  
   Перед началом работы над задачей всегда создавайте отдельную ветку:
   ```bash
   git checkout -b feature/add-login-screen
   ```

2. **Сделайте изменения и закоммитьте их**
   Пример: добавляем экран логина в Flutter-проекте.
   ```dart
   class LoginScreen extends StatelessWidget {
     @override
     Widget build(BuildContext context) {
       return Scaffold(
         appBar: AppBar(title: Text('Login')),
         body: Center(child: Text('Login Screen')),
       );
     }
   }
   ```

3. **Отправьте изменения на удалённый репозиторий**
   ```bash
   git push origin feature/add-login-screen
   ```

4. **Откройте MR через GitLab UI**
   - Перейдите в проект на GitLab.
   - Нажмите на вкладку **Merge Requests**.
   - Нажмите **New Merge Request**.
   - Выберите исходную (source) и целевую (target) ветки.
   - Укажите заголовок и описание MR.
   - Добавьте reviewers, если нужно.

### Что должно быть в описании MR?

Хорошее описание MR включает:
- Краткое описание изменений
- Ссылку на задачу (например, `Fixes #123`)
- Какие тесты были проведены
- Скриншоты или видео при необходимости

## 2. Как провести ревью MR

Ревью — это процесс проверки кода, который был предложен в MR. Он помогает избежать ошибок и улучшить качество кода.

### Что проверять при ревью?

#### ✅ Качество кода:
- Соответствие стилю кодирования (например, [Effective Dart](https://dart.dev/effective-dart))
- Правильное использование StatefulWidget/StatelessWidget
- Читаемость и структура

#### ❌ Ошибки:
- Неправильная обработка ошибок
- Утечки памяти
- Некорректная работа с асинхронными функциями

#### 🧪 Тестирование:
- Проверка на работоспособность
- Наличие unit/integration тестов (если применимо)

### Как проводить ревью через GitLab?

1. Перейдите в MR.
2. Прокрутите до секции **Changes**.
3. Выберите файл, который хотите проверить.
4. Нажмите на плюсик `+` рядом с строкой — можно оставить комментарий.
5. После проверки нажмите **Approve** или **Request changes**.

> 💡 Совет: Используйте **Code Review** в GitLab, чтобы оставлять комментарии к конкретным строкам кода. Это делает ревью более точным и полезным.

## 3. Как найти ненужные ветви Git

В процессе работы с Git могут появляться старые или ненужные ветки, которые уже не используются. Их нужно удалять, чтобы сохранить чистоту репозитория.

### Как найти старые или ненужные ветки?

#### Способ 1: Через GitLab UI
1. Перейдите в проект.
2. Нажмите **Repository > Branches**.
3. В списке веток можно увидеть дату последнего коммита. Если ветка не обновлялась долгое время — она может быть ненужной.

#### Способ 2: Через командную строку (локально)
```bash
git fetch --all --prune
```
Эта команда удаляет локальные ссылки на удалённые ветки, которые были удалены на сервере.

#### Способ 3: Использование скриптов
Можно написать простой скрипт на Bash или Python для поиска веток, которые не были изменены более 30 дней.

Пример:
```bash
git for-each-ref --format='%(committerdate:short) %(refname:short)' refs/heads/ | sort
```

### Как удалить ветку?

#### Локально:
```bash
git branch -d feature/add-login-screen
```

#### Удалённо (на GitLab):
```bash
git push origin --delete feature/add-login-screen
```

## 4. GitLab CI

**GitLab CI/CD** — это инструмент автоматизации, который позволяет запускать тесты, сборки и деплой автоматически при каждом изменении в репозитории.

### Основные компоненты GitLab CI:

- **.gitlab-ci.yml** — файл конфигурации CI/CD
- **Jobs** — отдельные задачи, которые выполняются
- **Pipelines** — набор задач, которые запускаются параллельно или последовательно

### Пример `.gitlab-ci.yml` для Flutter проекта

```yaml
# .gitlab-ci.yml

stages:
  - test
  - build

before_script:
  - echo "Installing dependencies"
  - flutter pub get

test:
  stage: test
  script:
    - flutter test
  only:
    - main
    - develop

build:
  stage: build
  script:
    - flutter build apk --release
  artifacts:
    paths:
      - build/app/outputs/flutter-apk/app-release.apk
  only:
    - main
```

### Что делает этот файл?

- Определяет этапы: `test` и `build`
- Запускает `flutter pub get`, чтобы установить зависимости
- Выполняет тесты при пуше в `main` или `develop`
- Собирает APK-файл при пуше в `main` и сохраняет его как артефакт

> 📝 Примечание: Для работы CI/CD нужно убедиться, что на сервере установлен Flutter и необходимые зависимости.

## Практическое задание

Создайте Flutter-проект в GitLab и выполните следующие действия:

1. Создайте локальный проект.
2. Закоммитьте изменения в отдельную ветку (например, `feature/new-screen`).
3. Отправьте ветку на GitLab.
4. Создайте Merge Request.
5. Попросите коллегу провести ревью.
6. После одобрения объедините MR.
7. Напишите `.gitlab-ci.yml`, который будет запускать тесты при каждом пуше в `main`.
