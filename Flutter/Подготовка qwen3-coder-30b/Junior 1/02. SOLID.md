# Лекция: SOLID-принципы в Flutter разработке

## Введение

Принципы SOLID — это фундаментальные правила проектирования программного обеспечения, которые помогают создавать гибкие, устойчивые и легко поддерживаемые приложения. Они особенно важны в мобильной разработке с Flutter, где архитектура и структура кода напрямую влияют на производительность и масштабируемость проекта.

В данной лекции мы рассмотрим каждый из пяти принципов SOLID и проиллюстрируем их применение на примерах на языке Dart и Flutter. Эти знания позволят вам создавать более качественный код, который будет легко расширяться, тестировать и менять в будущем.

---

## 1. Single Responsibility Principle (SRP) — Принцип единственной ответственности

### Описание

**Принцип единственной ответственности** гласит: *каждый класс должен выполнять только одну задачу или иметь одну причину для изменения.* Это означает, что если вы хотите изменить поведение класса, вы должны делать это по одной причине, а не по нескольким.

### Почему важно?

Если класс отвечает за несколько обязанностей, он становится сложным, трудно тестируемым и подверженным ошибкам. Это также усложняет его повторное использование.

### Как нарушить SRP?

Рассмотрим пример:

```dart
class User {
  String name;
  String email;

  void saveUser() {
    // Сохранение пользователя в БД
  }

  void sendEmail() {
    // Отправка письма пользователю
  }

  void validateUser() {
    // Валидация данных пользователя
  }
}
```

Здесь класс `User` выполняет сразу три задачи:
- управление данными пользователя (`name`, `email`)
- сохранение в БД (`saveUser`)
- отправка email (`sendEmail`)
- валидацию (`validateUser`)

Это нарушает SRP.

### Исправленный вариант

Разделим логику по отдельным классам:

```dart
class User {
  String name;
  String email;

  User(this.name, this.email);
}

class UserRepository {
  void save(User user) {
    // Сохраняем пользователя в БД
  }
}

class EmailService {
  void sendEmail(String to, String subject, String body) {
    // Отправляем письмо
  }
}

class UserValidator {
  bool validate(User user) {
    return user.email.isNotEmpty && user.name.isNotEmpty;
  }
}
```

Теперь каждый класс отвечает только за одну задачу.

## 2. Open-Closed Principle (OCP) — Принцип открытости/закрытости

### Описание

**Принцип открытости/закрытости** говорит о том, что *класс должен быть открыт для расширения, но закрыт для модификации*. То есть, вы можете добавлять новые функции, не изменяя уже существующий код.

### Старая трактовка

В классической интерпретации OCP требует, чтобы классы были написаны так, чтобы их можно было расширять без изменения исходного кода. Это обычно достигается через наследование и полиморфизм.

### Новая трактовка (с использованием интерфейсов)

Современная трактовка говорит о том, что вместо того, чтобы изменять классы, вы должны использовать **абстракции**, такие как интерфейсы или абстрактные классы, чтобы расширять поведение через реализации.

### Как нарушить OCP?

Пример нарушения:

```dart
class PaymentProcessor {
  void processPayment(PaymentMethod method) {
    if (method == PaymentMethod.creditCard) {
      // Обработка кредитной карты
    } else if (method == PaymentMethod.payPal) {
      // Обработка PayPal
    }
  }
}

enum PaymentMethod { creditCard, payPal }
```

Когда появляется новый способ оплаты (например, Apple Pay), мы должны изменить метод `processPayment`, что нарушает OCP.

### Исправленный вариант

Используем интерфейс:

```dart
abstract class PaymentProcessor {
  void process();
}

class CreditCardProcessor implements PaymentProcessor {
  @override
  void process() {
    print("Processing credit card payment");
  }
}

class PayPalProcessor implements PaymentProcessor {
  @override
  void process() {
    print("Processing PayPal payment");
  }
}
```

Теперь можно добавлять новые типы оплаты, просто реализуя интерфейс `PaymentProcessor`, не изменяя существующий код.

## 3. Liskov Substitution Principle (LSP) — Принцип подстановки Лисков

### Описание

**Принцип подстановки Лисков** гласит: *объекты могут быть заменены их наследниками без изменения корректности программы.* То есть, если класс `A` является подтипом класса `B`, то объекты типа `B` можно заменить объектами типа `A` без ошибок.

### Как нарушить LSP?

Пример нарушения:

```dart
class Rectangle {
  int width;
  int height;

  void setWidth(int w) => width = w;
  void setHeight(int h) => height = h;

  int getArea() => width * height;
}

class Square extends Rectangle {
  Square(int side) {
    width = side;
    height = side;
  }

  @override
  void setWidth(int w) {
    width = w;
    height = w; // Важно: и ширина, и высота становятся равны
  }

  @override
  void setHeight(int h) {
    width = h;
    height = h;
  }
}
```

В этом случае класс `Square` нарушает LSP, потому что при вызове методов `setWidth()` и `setHeight()` он ведёт себя иначе, чем его родитель `Rectangle`.

Представьте, вы написали функцию, которая ожидает объект типа `Rectangle`, но получает `Square`. При попытке установить ширину и высоту независимо друг от друга — возникнет ошибка.

### Исправление

Лучше избегать наследования между прямоугольниками и квадратами. Лучше использовать общий интерфейс:

```dart
abstract class Shape {
  int getArea();
}

class Rectangle implements Shape {
  int width;
  int height;

  Rectangle(this.width, this.height);

  @override
  int getArea() => width * height;
}

class Square implements Shape {
  int side;

  Square(this.side);

  @override
  int getArea() => side * side;
}
```

Теперь `Square` и `Rectangle` не наследуются друг от друга, а реализуют общий интерфейс — LSP соблюдается.

## 4. Interface Segregation Principle (ISP) — Принцип разделения интерфейсов

### Описание

**Принцип разделения интерфейсов** говорит: *клиенты не должны зависеть от интерфейсов, которые они не используют.* То есть, лучше создавать маленькие специализированные интерфейсы вместо одного большого.

### Как нарушить ISP?

Пример нарушения:

```dart
abstract class Worker {
  void work();
  void eat();
  void sleep();
}

class HumanWorker implements Worker {
  @override
  void work() => print("Human working");

  @override
  void eat() => print("Human eating");

  @override
  void sleep() => print("Human sleeping");
}

class RobotWorker implements Worker {
  @override
  void work() => print("Robot working");

  @override
  void eat() {
    // Робот не ест, но обязан реализовать метод
    throw UnimplementedError();
  }

  @override
  void sleep() {
    // Робот не спит, но обязан реализовать метод
    throw UnimplementedError();
  }
}
```

Здесь `RobotWorker` вынужден реализовывать методы, которые ему не нужны.

### Исправление

Разделим интерфейсы:

```dart
abstract class Workable {
  void work();
}

abstract class Eatable {
  void eat();
}

abstract class Sleepable {
  void sleep();
}

class HumanWorker implements Workable, Eatable, Sleepable {
  @override
  void work() => print("Human working");

  @override
  void eat() => print("Human eating");

  @override
  void sleep() => print("Human sleeping");
}

class RobotWorker implements Workable {
  @override
  void work() => print("Robot working");
}
```

Теперь каждый класс реализует только те интерфейсы, которые ему нужны.

## 5. Dependency Inversion Principle (DIP) — Принцип инверсии зависимостей

### Описание

**Принцип инверсии зависимостей** говорит: *модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций.* Также: *абстракции не должны зависеть от деталей, а детали должны зависеть от абстракций.*

### Как нарушить DIP?

Пример нарушения:

```dart
class EmailService {
  void sendEmail(String to, String body) {
    // Логика отправки email
  }
}

class NotificationService {
  final EmailService emailService = EmailService(); // Жестко завязано на реализацию

  void notify(String user) {
    emailService.sendEmail(user, "Hello!");
  }
}
```

Здесь `NotificationService` напрямую зависит от `EmailService`, что делает его не гибким.

### Исправление

Используем абстракцию:

```dart
abstract class NotificationSender {
  void send(String to, String message);
}

class EmailSender implements NotificationSender {
  @override
  void send(String to, String message) {
    print("Sending email to $to: $message");
  }
}

class NotificationService {
  final NotificationSender sender;

  NotificationService(this.sender);

  void notify(String user) {
    sender.send(user, "Hello!");
  }
}
```

Теперь `NotificationService` зависит от абстракции `NotificationSender`, и мы можем легко менять реализацию (например, на SMS или Push-уведомления).

### Отличие от Dependency Injection

**Dependency Injection (DI)** — это способ внедрения зависимостей в классы (например, через конструктор). **DIP** — это принцип проектирования, который говорит, что зависимости должны быть абстракциями. DI — это один из способов реализации DIP.
