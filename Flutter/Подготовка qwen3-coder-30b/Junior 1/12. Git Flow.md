# Лекция: Git Flow для Flutter-разработки

## Введение

Git Flow — это методология управления версиями, разработанная **Vincent Driessen** (в 2010 году). Она определяет структуру ветвлений и процесс работы с ними при разработке программного обеспечения. Git Flow особенно полезен для командной работы, где необходимо контролировать версии кода, управлять релизами и минимизировать конфликты.

Для Flutter-разработчиков Git Flow помогает организовать процесс разработки, тестирования и публикации приложений, особенно если вы работаете в команде или планируете выпускать несколько версий приложения.

---

## Основные ветви в Git Flow

Git Flow определяет несколько основных типов ветвлений:

### 1. **Master**
- Это ветка, содержащая только стабильный код.
- Каждый коммит в `master` соответствует релизу приложения.
- В этой ветке обычно находится последняя версия, готовая к публикации.

### 2. **Develop**
- Главная ветка разработки.
- Все новые функции и исправления сначала попадают в `develop`.
- Из `develop` создаются `release` ветки перед релизом.

### 3. **Feature**
- Ветви для разработки новых функций.
- Именуются обычно как `feature/<название-функции>`.
- Каждый разработчик работает в своей feature-ветке.

### 4. **Release**
- Ветка, используемая перед публикацией нового релиза.
- Все готовые к выпуску изменения из `develop` переносятся сюда.
- Здесь проводятся финальные тесты и исправления.

### 5. **Hotfix**
- Используется для срочных исправлений, когда нужно быстро выпустить исправление в уже опубликованную версию.
- Имя обычно: `hotfix/<название-исправления>`.

## Подробное описание работы с ветвями

### 🌿 1. Ветка **Master**

Эта ветка — «железный» источник кода для релизов. Каждый коммит здесь должен быть стабильным и протестированным.

#### Пример:
```bash
git checkout -b master
```
После публикации релиза вы делаете тег:
```bash
git tag -a v1.0.0 -m "Релиз версии 1.0.0"
```

### 🧱 2. Ветка **Develop**

Основная ветка, куда все изменения сначала попадают. Она содержит все последние разработки.

#### Пример:
```bash
git checkout -b develop origin/develop
```
Здесь вы работаете над новыми функциями и исправлениями.

### 🧩 3. Ветка **Feature**

Каждая новая функция создаётся в отдельной `feature`-ветке.

#### Пример:
```bash
git checkout -b feature/user-login develop
```
После завершения работы над функцией:
```bash
git checkout develop
git merge --no-ff feature/user-login
git branch -d feature/user-login
```

> **Примечание**: `--no-ff` означает, что вы создаёте новый коммит при слиянии, чтобы сохранить историю ветвления.

### 📦 4. Ветка **Release**

Используется перед публикацией нового релиза.

#### Пример:
```bash
git checkout -b release/2.0.0 develop
```
Здесь можно провести финальные тесты и сделать финальные исправления.

Когда всё готово:
```bash
git checkout master
git merge --no-ff release/2.0.0
git tag -a v2.0.0 -m "Релиз версии 2.0.0"
```
Также нужно смерджить изменения обратно в `develop`:
```bash
git checkout develop
git merge --no-ff release/2.0.0
git branch -d release/2.0.0
```

### 🔧 5. Ветка **Hotfix**

Используется для срочных исправлений, когда нужно быстро выпустить патч.

#### Пример:
```bash
git checkout -b hotfix/bug-fix master
```
После исправления:
```bash
git checkout master
git merge --no-ff hotfix/bug-fix
git tag -a v1.0.1 -m "Исправление ошибки в версии 1.0.1"

git checkout develop
git merge --no-ff hotfix/bug-fix
git branch -d hotfix/bug-fix
```

## Действия при доработке веток **Develop** и **Release**

### 🔄 Работа с **Develop**

В `develop` происходит постоянная интеграция новых функций.

- Все feature-ветки мержатся в `develop`.
- Если вы обнаружили ошибку, которая должна быть исправлена в следующем релизе — создайте **hotfix** ветку от `master`.

### 🧪 Работа с **Release**

Когда вы готовы к релизу:

1. Создайте `release/<версия>` ветку от `develop`.
2. Проведите тестирование.
3. Исправьте ошибки, если есть.
4. Запустите финальные тесты.
5. После завершения — мержите в `master` и `develop`.

---

## Действия при публикации релизов

### ✅ Публикация релиза:

1. Создайте ветку `release/<версия>` от `develop`.
2. Убедитесь, что все функции протестированы.
3. Проведите финальные тесты и исправьте ошибки.
4. После завершения — мержите `release` в `master`.
5. Создайте тег:
   ```bash
   git tag -a v2.0.0 -m "Релиз версии 2.0.0"
   ```
6. Мержите `release` обратно в `develop`, чтобы все изменения остались там.
7. Удалите `release` ветку:
   ```bash
   git branch -d release/2.0.0
   ```

## Пример: Полный процесс разработки и релиза

Допустим, вы работаете над Flutter-приложением и используете Git Flow.

### 1. Начало работы:
```bash
git checkout -b develop origin/develop
```

### 2. Создание новой функции:
```bash
git checkout -b feature/user-authentication develop
```

### 3. После завершения разработки:
```bash
git checkout develop
git merge --no-ff feature/user-authentication
git branch -d feature/user-authentication
```

### 4. Подготовка к релизу:
```bash
git checkout -b release/2.1.0 develop
```

### 5. Финальные тесты и исправления:
(Вы работаете в `release` ветке)

### 6. Публикация релиза:
```bash
git checkout master
git merge --no-ff release/2.1.0
git tag -a v2.1.0 -m "Релиз версии 2.1.0"
```

### 7. Обновление `develop`:
```bash
git checkout develop
git merge --no-ff release/2.1.0
git branch -d release/2.1.0
```

## Практическое задание

**Задача**: Представьте, что вы работаете над Flutter-приложением, которое уже имеет версию 1.0.0. У вас есть следующие задачи:

1. Добавить функционал «Авторизация через Google».
2. Исправить баг с отображением списка пользователей.
3. Выпустить релиз 1.1.0.

**Что нужно сделать:**

1. Создайте feature-ветку для авторизации.
2. Сделайте коммиты с изменениями в этой ветке.
3. Завершите работу и смержите её в `develop`.
4. Создайте hotfix-ветку для бага с отображением списка.
5. Исправьте проблему, смержите в `develop` и `master`.
6. Подготовьте релиз 1.1.0, создайте тег.

**После выполнения задания:**
- Сделайте `git log --oneline --graph --all` и убедитесь, что структура ветвей соответствует Git Flow.
- Отправьте изменения на удалённый репозиторий.
