# **Лекция: iOS. Устранение утечек памяти**

## **Введение**

При разработке мобильных приложений на Flutter важно понимать, как управляется память в iOS (и Android), особенно если вы работаете с нативными плагинами или используете Objective-C/Swift код внутри Flutter-приложения. В этой лекции мы рассмотрим:

1. Какие проблемы могут привести к утечкам памяти.
2. Как искать утечки с помощью **Instruments**.
3. Как использовать **Memory Graph** для анализа ссылок.
4. Как предотвратить такие ошибки при разработке Flutter-приложений.

Эта тема особенно важна для разработчиков уровня **Middle 3 iOS**, так как утечки памяти могут привести к:
- Падению приложения,
- Снижению производительности,
- Неправильной работе с асинхронными задачами.

## **1. Как сделать утечку памяти в iOS?**

Утечка памяти происходит, когда объекты создаются, но не освобождаются из памяти, даже если они больше не нужны. Это приводит к накоплению объектов в памяти и, в конечном счёте — к **Memory Warning** и **crash-ам**.

### 📌 Основные причины утечек:

#### 1. **Циклические ссылки (Retain Cycles)**
Это самая распространённая причина утечек в Swift.

##### Пример:

```swift
class Person {
    let name: String
    var pet: Pet?

    init(name: String) {
        self.name = name
    }

    deinit {
        print("\(name) is being deinitialized")
    }
}

class Pet {
    let name: String
    weak var owner: Person? // Используем weak, чтобы избежать цикла

    init(name: String) {
        self.name = name
    }

    deinit {
        print("\(name) is being deinitialized")
    }
}
```

Если убрать `weak` у `owner`, то будет циклическая ссылка:

```swift
let person = Person(name: "John")
let pet = Pet(name: "Fluffy")

person.pet = pet
pet.owner = person

// Теперь они не будут освобождены, даже если выйти из области видимости
```

##### Решение:
Используйте `weak` или `unowned` для ссылок, которые могут создать цикл.

---

#### 2. **Замыкания (Closures)**
Если замыкание захватывает `self`, и `self` также захватывает замыкание — возникает утечка.

##### Пример:

```swift
class ViewController: UIViewController {
    var data = [String]()

    override func viewDidLoad() {
        super.viewDidLoad()

        // ❌ Утечка: self захватывается в closure
        fetchData { [weak self] result in
            self?.data = result
        }
    }

    func fetchData(completion: @escaping ([String]) -> Void) {
        DispatchQueue.main.asyncAfter(deadline: .now() + 1) {
            completion(["item1", "item2"])
        }
    }
}
```

Если не использовать `[weak self]`, то `self` будет захвачен и не освобождён.

---

#### 3. **Диспетчеры событий (Delegates, Observers)**
Если вы подписываетесь на события, например, через `NotificationCenter`, но не отписываетесь — объект остаётся в памяти.

##### Пример:

```swift
class MyViewController: UIViewController {
    override func viewDidLoad() {
        super.viewDidLoad()

        NotificationCenter.default.addObserver(
            self,
            selector: #selector(handleNotification),
            name: NSNotification.Name("SomeNotification"),
            object: nil
        )
    }

    @objc private func handleNotification(_ notification: Notification) {
        // ...
    }

    deinit {
        NotificationCenter.default.removeObserver(self)
    }
}
```

Если забыть `removeObserver`, то объект не будет удалён.

---

#### 4. **Использование `strong` ссылок в `Timer` или `CADisplayLink`**
Таймеры и другие периодические объекты могут держать объект в памяти, если не освобождаются.

##### Пример:

```swift
class MyViewController: UIViewController {
    var timer: Timer?

    override func viewDidLoad() {
        super.viewDidLoad()

        // ❌ Утечка: self захватывается таймером
        timer = Timer.scheduledTimer(withTimeInterval: 1.0, repeats: true) { _ in
            print("Timer fired")
        }
    }

    deinit {
        timer?.invalidate()
    }
}
```

## **2. Поиск утечек памяти с помощью Instruments**

**Instruments** — это мощный инструмент от Apple, позволяющий анализировать использование памяти, CPU и другие ресурсы.

### 🔧 Как использовать Instruments для поиска утечек:

#### 1. Откройте Xcode → Product → Profile
Выберите **Leaks** или **Allocations** инструмент.

#### 2. Выберите приложение (если вы тестируете Flutter-приложение, используйте `flutter build ios` и запустите на устройстве)

#### 3. Нажмите «Record» и выполните действия в вашем приложении

#### 4. Остановите запись и посмотрите на:
- Утечки памяти (выделение памяти, которое не освобождается)
- Статистику по объектам
- Историю создания объектов

##### Пример: Проверка утечек в приложении

1. Запустите приложение.
2. Нажмите на кнопку, которая вызывает асинхронную задачу (например, загрузку данных).
3. В Instruments отслеживайте объекты, которые не освобождаются.

#### 5. Фильтрация по типам:
- Используйте фильтры в **Allocations** для поиска конкретных классов.
- Следите за количеством живых объектов и их жизненным циклом.

## **3. Анализ ссылок на объекты с помощью Memory Graph**

Memory Graph — это инструмент, доступный в Xcode, который показывает, как связаны объекты в памяти в реальном времени.

### 🔍 Как использовать Memory Graph:

1. Запустите приложение в Xcode.
2. В Debug Area → Memory Graph Debugger (или нажмите `View` → Debug Area → Memory Graph)
3. Нажмите на кнопку «Capture»
4. Выберите объект и посмотрите:
   - Кто ссылается на него (`strong` или `weak`)
   - Есть ли циклические ссылки
   - Какие объекты живут в памяти

### 📌 Пример анализа:

Во время отладки, если вы видите, что `ViewController` не уничтожается, и в Memory Graph показано, что он ссылается на себя (через замыкание или делегат), значит есть утечка.

## **4. Практические рекомендации для Flutter-разработчиков**

1. **Не используйте `strong` ссылки в замыканиях без необходимости**
   - Используйте `[weak self]` или `[unowned self]`

2. **Отписывайтесь от NotificationCenter, KVO, Timer и других подписок**
   - В `deinit` всегда вызывайте `removeObserver`, `invalidate`, `removeFromSuperview`, и т.д.

3. **Используйте `weak` для делегатов и `IBOutlet`**
   - Если вы используете делегаты или `@IBOutlet`, они могут стать причиной циклических ссылок

4. **Не забывайте про нативные плагины**
   - Если вы используете Swift/ObjC код в Flutter, убедитесь, что он не вызывает утечек памяти.
